# 에이전트 스킬 사용하기

## Overview

Agent Skills는 개발 단계별로 정리된 엔지니어링 워크플로 스킬 모음이다. 각 스킬은 시니어 엔지니어가 따르는 특정한 절차를 담고 있다. 이 메타 스킬은 현재 작업에 맞는 스킬을 찾아 적절히 적용하도록 돕는다.

## When to Use

- 세션을 시작할 때
- 현재 작업에 어떤 스킬을 적용해야 할지 불분명할 때
- 여러 스킬을 어떤 순서로 연결해야 할지 판단해야 할 때
- 작업 흐름을 표준화된 개발 단계로 정리하고 싶을 때

## 스킬 찾기

작업이 들어오면 먼저 개발 단계를 식별하고, 그에 맞는 스킬을 적용한다.

```
Task arrives
    │
    ├── 아이디어가 모호하거나 다듬어야 하나? ──→ idea-refine
    ├── 새 프로젝트/기능/변경인가? ───────────→ spec-driven-development
    ├── 명세는 있고 작업 분해가 필요한가? ───→ planning-and-task-breakdown
    ├── 코드를 구현 중인가? ─────────────────→ incremental-implementation
    │   ├── UI 작업인가? ───────────────────→ frontend-ui-engineering
    │   ├── API 작업인가? ──────────────────→ api-and-interface-design
    │   └── 더 나은 문맥이 필요한가? ───────→ context-engineering
    ├── 테스트를 쓰거나 실행 중인가? ───────→ test-principal
    │   └── 브라우저 기반인가? ─────────────→ browser-testing-with-devtools
    ├── 뭔가 망가졌는가? ───────────────────→ debugging-and-error-recovery
    ├── 코드를 리뷰하는 중인가? ────────────→ code-review-and-quality
    │   ├── 보안 이슈가 있는가? ───────────→ security-and-hardening
    │   └── 성능 이슈가 있는가? ───────────→ performance-optimization
    ├── 커밋/브랜치 작업인가? ───────────────→ git-workflow-and-versioning
    ├── CI/CD 파이프라인 작업인가? ────────→ ci-cd-and-automation
    ├── 문서/ADR 작성인가? ────────────────→ documentation-and-adrs
    └── 배포/출시 작업인가? ───────────────→ shipping-and-launch
```

## 핵심 운영 습관

이 습관들은 모든 스킬에 공통으로 적용된다. 예외 없이 지켜야 한다.

### 1. 가정을 드러내기

사소하지 않은 작업을 구현하기 전에, 자신이 두고 있는 가정을 명시적으로 적는다.

```
ASSUMPTIONS I'M MAKING:
1. [요구사항에 대한 가정]
2. [아키텍처에 대한 가정]
3. [범위에 대한 가정]
→ 틀렸다면 지금 바로 정정해 주세요. 아니면 이 가정으로 진행합니다.
```

모호한 요구사항을 조용히 메우지 마라. 가장 흔한 실패는 잘못된 가정을 검증 없이 밀어붙이는 것이다. 불확실성은 일찍 드러낼수록 재작업 비용이 줄어든다.

### 2. 혼란을 적극적으로 관리하기

불일치, 충돌하는 요구사항, 불명확한 명세를 만나면:

1. **멈춘다.** 추측으로 진행하지 않는다.
2. 무엇이 헷갈리는지 구체적으로 이름 붙인다.
3. 트레이드오프를 설명하거나 확인 질문을 던진다.
4. 정리가 끝날 때까지 기다린다.

**나쁜 예:** 해석 하나를 조용히 선택하고 맞기를 바라는 것  
**좋은 예:** "명세에는 X가 있는데 기존 코드에는 Y가 있습니다. 무엇을 우선해야 하나요?"

### 3. 필요할 때는 반대하기

당신은 무조건 "예"라고 답하는 기계가 아니다. 접근 방식에 명확한 문제가 있으면:

- 문제를 직접 지적한다.
- 구체적 손해를 설명한다. 가능하면 수치로 말한다. "조금 느릴 수 있다"보다 "지연이 약 200ms 늘어난다"가 낫다.
- 대안을 제시한다.
- 사람이 충분한 정보를 가진 상태에서 override하면 그 판단은 받아들인다.

아첨은 실패 모드다. "물론이죠!"라고 말한 뒤 나쁜 아이디어를 구현하는 것은 아무에게도 도움이 되지 않는다. 솔직한 기술적 이견이 거짓 동의보다 낫다.

### 4. 단순함을 강제하기

당신은 본능적으로 과하게 복잡하게 만들기 쉽다. 그 성향을 의식적으로 억제한다.

구현을 끝내기 전에 스스로 묻는다.

- 더 적은 줄 수로 해결할 수 없는가?
- 이 추상화는 정말 복잡도를 정당화하는가?
- 스태프 엔지니어가 봤을 때 "그냥 이렇게 하면 되잖아?"라고 말하지 않을까?

100줄이면 될 일을 1000줄로 만들었다면 실패다. 눈에 띄지 않고 뻔한 해법을 선호하라. 영리함은 비용이 크다.

### 5. 범위를 지키기

요청받은 부분만 건드린다.

다음은 하지 않는다.

- 이해하지 못한 주석 삭제
- 작업과 무관한 코드 "정리"
- 인접한 시스템을 부수적으로 리팩터링
- 확실히 알지 못하는 미사용 코드 삭제
- 명세에 없는 기능을 "유용해 보여서" 추가

당신의 역할은 외과적 정밀함이지, 멋대로 하는 리모델링이 아니다.

### 6. 추측하지 말고 검증하기

모든 스킬에는 검증 단계가 있다. 검증이 통과하기 전에는 작업이 끝난 것이 아니다. "맞아 보인다"는 충분한 근거가 아니다. 테스트 통과, 빌드 출력, 런타임 데이터 같은 증거가 있어야 한다.

## 피해야 할 실패 모드

겉보기에는 생산성처럼 보이지만 실제로는 문제를 만드는 미묘한 실수들이다.

1. 확인하지 않은 채 잘못된 가정을 세우는 것
2. 스스로의 혼란을 관리하지 않고 막 밀어붙이는 것
3. 눈에 띈 불일치를 드러내지 않는 것
4. 자명하지 않은 결정에서 트레이드오프를 설명하지 않는 것
5. 명백한 문제가 있는 접근에 아첨하는 것
6. 코드와 API를 과도하게 복잡하게 만드는 것
7. 작업과 무관한 코드나 주석을 수정하는 것
8. 충분히 이해하지 못한 것을 제거하는 것
9. "뻔하다"는 이유로 명세 없이 바로 만드는 것
10. "맞아 보인다"는 이유로 검증을 건너뛰는 것

## 스킬 규칙

1. **작업을 시작하기 전에 적용 가능한 스킬이 있는지 먼저 확인한다.** 스킬은 반복되는 실수를 막아 주는 절차다.

2. **스킬은 권고가 아니라 워크플로다.** 순서대로 따르고, 검증 단계는 건너뛰지 않는다.

3. **여러 스킬이 함께 적용될 수 있다.** 기능 구현 하나에도 `idea-refine` → `spec-driven-development` → `planning-and-task-breakdown` → `incremental-implementation` → `test-principal` → `code-review-and-quality` → `shipping-and-launch` 순서가 연달아 쓰일 수 있다.

4. **애매하면 명세부터 시작한다.** 작업이 사소하지 않고 명세가 없다면 `spec-driven-development`부터 시작한다.

## 라이프사이클 순서

완전한 기능 하나를 처리할 때의 일반적인 스킬 순서는 다음과 같다.

```
1. idea-refine                 → 모호한 아이디어를 다듬는다
2. spec-driven-development     → 무엇을 만들지 정의한다
3. planning-and-task-breakdown → 검증 가능한 단위로 쪼갠다
4. context-engineering         → 필요한 문맥만 정확히 불러온다
5. incremental-implementation  → 얇은 수직 슬라이스로 구현한다
6. test-principal     → 각 슬라이스가 동작함을 증명한다
7. code-review-and-quality     → 머지 전에 리뷰한다
8. git-workflow-and-versioning → 커밋 이력을 정돈한다
9. documentation-and-adrs      → 결정을 문서화한다
10. shipping-and-launch        → 안전하게 배포한다
```

모든 작업이 모든 스킬을 필요로 하지는 않는다. 예를 들어 버그 수정은 `debugging-and-error-recovery` → `test-principal` → `code-review-and-quality`만으로 충분할 수 있다.

## 빠른 참조

| Phase | Skill | One-Line Summary |
|-------|-------|-----------------|
| Define | idea-refine | 발산과 수렴을 거쳐 아이디어를 구조적으로 정제한다 |
| Define | spec-driven-development | 코드 전에 요구사항과 승인 기준을 정의한다 |
| Plan | planning-and-task-breakdown | 검증 가능한 작은 작업으로 분해한다 |
| Build | incremental-implementation | 얇은 수직 슬라이스를 만들고 단계적으로 확장한다 |
| Build | context-engineering | 필요한 문맥을 필요한 시점에만 불러온다 |
| Build | frontend-ui-engineering | 접근성을 포함한 프로덕션급 UI를 만든다 |
| Build | api-and-interface-design | 계약이 분명한 안정적인 인터페이스를 설계한다 |
| Verify | test-principal | 구현 직후 테스트를 작성해 동작을 증명한다 |
| Verify | browser-testing-with-devtools | Chrome DevTools MCP로 런타임을 검증한다 |
| Verify | debugging-and-error-recovery | 재현 → 국소화 → 수정 → 회귀 방지 순서로 해결한다 |
| Review | code-review-and-quality | 다섯 축 기준으로 품질 게이트를 적용한다 |
| Review | security-and-hardening | OWASP 예방, 입력 검증, 최소 권한을 점검한다 |
| Review | performance-optimization | 먼저 측정하고, 중요한 것만 최적화한다 |
| Ship | git-workflow-and-versioning | 원자적 커밋과 깨끗한 이력을 유지한다 |
| Ship | ci-cd-and-automation | 모든 변경에 자동 품질 게이트를 건다 |
| Ship | documentation-and-adrs | 무엇보다 왜 그렇게 했는지 기록한다 |
| Ship | shipping-and-launch | 출시 전 점검, 모니터링, 롤백 계획을 갖춘다 |

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "대충 맞아 보이는 스킬로 시작하면 된다" | 잘못된 스킬로 시작하면 뒤 단계 전체가 흔들린다. 먼저 현재 작업 단계부터 식별해야 한다. |
| "메타 스킬은 없어도 된다" | 어떤 스킬을 언제 적용할지 모르면 좋은 스킬 모음도 활용되지 않는다. |
| "일단 구현부터 하고 나중에 맞는 스킬을 붙이자" | 스킬의 가치는 순서를 강제해 실수를 줄이는 데 있다. 나중에 붙이면 이미 늦다. |
| "하나의 스킬만 알면 충분하다" | 실제 작업은 정의, 계획, 구현, 검증, 리뷰, 배포가 연결된 흐름이다. 여러 스킬을 조합해야 한다. |

## Red Flags

- 작업을 시작했는데 어떤 스킬을 적용 중인지 설명할 수 없는 경우
- 명세가 없는데도 바로 구현으로 들어가는 경우
- 검증과 리뷰 단계를 스킵하는 경우
- 서로 다른 문제 유형에 같은 스킬만 반복해서 적용하는 경우
- 작업과 무관한 스킬을 억지로 끼워 넣는 경우

## Verification

메타 스킬을 적용한 뒤에는 다음을 확인한다.

- [ ] 현재 작업의 단계와 맞는 스킬을 선택했다.
- [ ] 필요한 경우 둘 이상의 스킬 순서를 명시했다.
- [ ] 비사소한 작업이라면 구현 전에 `spec-driven-development` 적용 여부를 점검했다.
- [ ] 구현 작업이라면 검증과 리뷰 스킬까지 포함한 흐름을 잡았다.

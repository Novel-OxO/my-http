# 코드 리뷰와 품질

## Overview

품질 게이트를 갖춘 다차원 코드 리뷰다. 모든 변경은 머지 전에 반드시 리뷰한다. 예외는 없다. 리뷰는 정확성, 가독성, 아키텍처, 보안, 성능의 다섯 축으로 진행한다.

**승인 기준:** 완벽하지 않더라도 코드베이스의 전반적인 건강 상태를 확실히 개선한다면 승인한다. 완벽한 코드는 없다. 목표는 지속적인 개선이다. 단지 "내가 짰다면 다르게 짰을 것"이라는 이유로 막지 마라.
코드베이스 관례를 따르고 전체적으로 좋아진다면 승인한다.

## When to Use

- PR이나 변경을 머지하기 전에
- 기능 구현을 마친 직후
- 다른 에이전트나 모델이 만든 코드를 평가할 때
- 기존 코드를 리팩터링한 뒤
- 버그 수정 후. 수정 내용과 회귀 테스트를 함께 검토해야 한다

## 다섯 축 리뷰

모든 리뷰는 아래 기준으로 평가한다.

### 1. 정확성

이 코드는 스스로 주장하는 일을 실제로 하는가?

- 명세나 작업 요구사항과 일치하는가?
- null, 빈 값, 경계값 같은 엣지 케이스를 처리하는가?
- happy path뿐 아니라 오류 경로도 처리하는가?
- 모든 테스트를 통과하는가? 그리고 테스트가 실제로 올바른 것을 검증하는가?
- off-by-one, 경쟁 상태, 상태 불일치가 있는가?

### 2. 가독성과 단순성

작성자의 설명 없이도 다른 엔지니어나 에이전트가 이해할 수 있는가?

- 이름이 설명적이며 프로젝트 관례와 일관적인가? 맥락 없는 `temp`, `data`, `result` 같은 이름은 없는가?
- 제어 흐름이 단순한가? 중첩 삼항식이나 깊은 콜백은 피했는가?
- 관련 코드가 묶여 있고 모듈 경계가 분명한가?
- 괜히 영리한 트릭이 들어가 있지 않은가? 단순화할 수 없는가?
- **더 적은 줄 수로 할 수 없는가?** 100줄이면 될 일을 1000줄로 만들면 실패다.
- **추상화가 그 복잡도를 정당화하는가?** 세 번째 사용 사례가 나오기 전까지 일반화하지 마라.
- 명확하지 않은 의도를 설명할 주석이 필요한가? 단, 뻔한 코드를 주석으로 설명하지는 마라.
- no-op 변수, 하위 호환 셈(shim), `// removed` 같은 죽은 코드 흔적이 남아 있지 않은가?

### 3. 아키텍처

이 변경은 시스템 설계에 잘 맞는가?

- 기존 패턴을 따르는가, 아니면 새 패턴을 도입하는가? 새롭다면 정당한가?
- 모듈 경계를 깨끗하게 유지하는가?
- 공용화해야 할 중복 코드가 있는가?
- 의존성 방향이 올바른가? 순환 참조는 없는가?
- 추상화 수준이 적절한가? 과설계도 아니고 과하게 결합되지도 않았는가?

### 4. 보안

보안 가이드는 `security-and-hardening`을 참고한다. 이 변경이 취약점을 만들지는 않는가?

- 사용자 입력을 검증하고 정제하는가?
- 비밀 정보가 코드, 로그, 버전 관리에 남지 않는가?
- 필요한 곳에서 인증과 인가를 확인하는가?
- SQL 쿼리는 문자열 연결이 아니라 파라미터 바인딩을 쓰는가?
- 출력은 XSS를 막도록 인코딩되는가?
- 의존성은 신뢰 가능한 출처이며 알려진 취약점이 없는가?
- API, 로그, 사용자 콘텐츠, 설정 파일 같은 외부 데이터는 신뢰하지 않는가?
- 외부 데이터 흐름은 로직이나 렌더링에 쓰기 전에 시스템 경계에서 검증되는가?

### 5. 성능

자세한 최적화 가이드는 `performance-optimization`을 참고한다. 이 변경이 성능 문제를 만들지는 않는가?

- N+1 쿼리 패턴이 있는가?
- 제한 없는 루프나 데이터 조회가 있는가?
- 비동기로 해야 할 작업을 동기로 처리하고 있지는 않은가?
- UI에서 불필요한 재렌더링이 생기지 않는가?
- 목록 엔드포인트에 페이지네이션이 빠져 있지 않은가?
- hot path에서 큰 객체를 계속 만들고 있지 않은가?

## 변경 크기 관리

작고 집중된 변경이 리뷰하기 쉽고, 머지하기 빠르며, 배포도 안전하다. 목표 크기는 다음과 같다.

```
~100 lines changed   → 좋다. 한 번에 리뷰할 수 있다.
~300 lines changed   → 하나의 논리적 변경이라면 수용 가능하다.
~1000 lines changed  → 너무 크다. 나눠라.
```

**"하나의 변경"이란 무엇인가:** 하나의 문제를 해결하고, 관련 테스트를 포함하며, 제출 직후에도 시스템이 동작하는 자기완결적 수정 하나를 뜻한다. 기능 전체가 아니라 기능의 한 조각이다.

**변경이 너무 클 때 나누는 방법**

| Strategy | How | When |
|----------|-----|------|
| **Stack** | 작은 변경을 먼저 올리고, 다음 변경을 그 위에 쌓는다 | 순차 의존성이 있을 때 |
| **By file group** | 다른 리뷰어가 봐야 하는 파일 그룹별로 나눈다 | 횡단 관심사가 있을 때 |
| **Horizontal** | 공용 코드나 스텁을 먼저 만들고 소비자를 나중에 붙인다 | 계층형 아키텍처일 때 |
| **Vertical** | 기능을 더 작은 end-to-end 슬라이스로 나눈다 | 기능 개발일 때 |

**큰 변경이 허용되는 경우:** 파일 전체 삭제나 자동 리팩터링처럼, 리뷰어가 모든 줄 대신 의도를 검증하면 되는 경우다.

**리팩터링과 기능 변경은 분리한다.** 기존 코드를 리팩터링하면서 새 동작도 추가했다면 그것은 두 개의 변경이다. 변수명 정리 같은 작은 정리는 리뷰어 판단하에 함께 넣을 수 있다.

## 변경 설명

모든 변경은 버전 관리 기록만 봐도 이해되는 설명이 필요하다.

**첫 줄:** 짧고, 명령형이고, 단독으로 읽혀야 한다. "Deleting the FizzBuzz RPC"가 아니라 "Delete the FizzBuzz RPC"다. 검색 히스토리에서 diff를 열지 않아도 무슨 변경인지 알 수 있어야 한다.

**본문:** 무엇이 왜 바뀌는지 쓴다. 코드만 봐서는 드러나지 않는 맥락, 결정, 이유를 담는다. 필요하면 버그 번호, 벤치마크 결과, 설계 문서에 링크한다. 접근 방식에 한계가 있다면 숨기지 않고 적는다.

**안 좋은 예:** "Fix bug", "Fix build", "Add patch", "Moving code from A to B", "Phase 1", "Add convenience functions"

## 리뷰 절차

### 1단계: 문맥 이해하기

코드를 보기 전에 의도를 이해한다.

```
- 이 변경은 무엇을 이루려는가?
- 어떤 명세나 작업을 구현하는가?
- 기대되는 동작 변화는 무엇인가?
```

### 2단계: 테스트부터 보기

테스트는 의도와 커버리지를 드러낸다.

```
- 이 변경에 대한 테스트가 존재하는가?
- 구현 세부사항이 아니라 동작을 테스트하는가?
- 엣지 케이스를 다루는가?
- 테스트 이름이 설명적인가?
- 코드가 바뀌었을 때 회귀를 잡아낼 수 있는가?
```

### 3단계: 구현 리뷰하기

다섯 축을 염두에 두고 코드를 순회한다.

```
For each file changed:
1. Correctness: 테스트가 요구하는 동작을 실제로 하는가?
2. Readability: 도움 없이 이해할 수 있는가?
3. Architecture: 시스템에 잘 맞는가?
4. Security: 취약점은 없는가?
5. Performance: 병목은 없는가?
```

### 4단계: 피드백 심각도 분류하기

작성자가 무엇을 반드시 고쳐야 하는지 알 수 있도록 모든 코멘트에 심각도를 붙인다.

| Prefix | Meaning | Author Action |
|--------|---------|---------------|
| *(no prefix)* | Required change | 머지 전에 반드시 수정 |
| **Critical:** | Blocks merge | 보안 취약점, 데이터 손실, 기능 파손 |
| **Nit:** | Minor, optional | 작성자가 무시해도 되는 사소한 의견 |
| **Optional:** / **Consider:** | Suggestion | 고려할 가치는 있지만 필수는 아님 |
| **FYI** | Informational only | 맥락 전달용, 별도 조치 불필요 |

이 분류가 없으면 작성자는 모든 피드백을 필수로 받아들이고 불필요한 시간을 쓰게 된다.

### 5단계: 검증 스토리 검토하기

작성자가 어떤 방식으로 검증했는지 확인한다.

```
- 어떤 테스트를 돌렸는가?
- 빌드는 통과했는가?
- 수동 검증을 했는가?
- UI 변경이라면 스크린샷이 있는가?
- before/after 비교가 있는가?
```

## 멀티모델 리뷰 패턴

서로 다른 리뷰 관점을 위해 다른 모델을 활용한다.

```
Model A writes the code
    │
    ▼
Model B reviews for correctness and architecture
    │
    ▼
Model A addresses the feedback
    │
    ▼
Human makes the final call
```

이렇게 하면 하나의 모델이 놓칠 수 있는 지점을 다른 모델이 잡아낼 수 있다.

**리뷰 에이전트 프롬프트 예시**

```
Review this code change for correctness, security, and adherence to
our project conventions. The spec says [X]. The change should [Y].
Flag any issues as Critical, Important, or Suggestion.
```

## 죽은 코드 위생

리팩터링이나 구현 변경 뒤에는 고아 코드가 남았는지 확인한다.

1. 더 이상 도달되지 않거나 사용되지 않는 코드를 찾는다.
2. 그 목록을 명시적으로 적는다.
3. **지우기 전에 묻는다:** "이제 쓰이지 않는 아래 요소들을 제거할까요: [list]?"

죽은 코드를 방치하지 마라. 미래의 사람과 에이전트를 헷갈리게 만든다. 하지만 확실치 않은 것을 조용히 지우지도 마라. 확신이 없으면 묻는다.

```
DEAD CODE IDENTIFIED:
- formatLegacyDate() in src/utils/date.ts — formatDate()로 대체됨
- OldTaskCard component in src/components/ — TaskCard로 대체됨
- LEGACY_API_URL constant in src/config.ts — 더 이상 참조 없음
→ 이것들을 제거해도 될까요?
```

## 리뷰 속도

느린 리뷰는 팀 전체를 막는다. 리뷰를 위해 컨텍스트를 전환하는 비용보다, 다른 사람을 기다리게 만드는 비용이 더 크다.

- **영업일 기준 하루 안에는 응답한다.** 최대치일 뿐이며 목표는 더 빠른 응답이다.
- **이상적인 리듬:** 리뷰 요청이 오면, 깊은 집중 작업 중이 아니라면 가능한 빨리 반응한다. 보통 규모의 변경은 하루 안에 여러 번 왕복될 수 있어야 한다.
- **최종 승인보다 개별 응답 속도를 우선한다.** 빠른 피드백은 여러 라운드가 필요하더라도 대기 시간을 크게 줄인다.
- **변경이 너무 크면:** 억지로 리뷰하지 말고 나누라고 요구한다.

## 이견 처리

리뷰 의견이 충돌할 때는 다음 우선순위를 따른다.

1. **기술적 사실과 데이터**가 의견보다 우선한다.
2. **스타일 가이드**는 스타일 문제에서 절대 기준이다.
3. **소프트웨어 설계**는 개인 취향이 아니라 엔지니어링 원칙으로 평가해야 한다.
4. **코드베이스 일관성**은 전체 건강을 해치지 않는 한 존중할 수 있다.

**"나중에 정리할게요"를 받아들이지 마라.** 경험상 나중은 오지 않는다. 진짜 긴급 상황이 아니라면 제출 전에 정리하게 해야 한다. 주변 문제를 이번 변경에서 다룰 수 없다면, 본인에게 할당된 버그를 만들게 하라.

## 리뷰에서의 정직함

자신, 다른 에이전트, 사람 누구의 코드를 리뷰하든:

- **형식적으로 승인하지 마라.** 실제 검토 근거 없이 "LGTM"만 적는 것은 아무 의미가 없다.
- **실제 문제를 약하게 말하지 마라.** 운영에서 터질 버그를 "사소한 우려일 수도 있다"라고 포장하는 것은 정직하지 않다.
- **가능하면 수치화하라.** "이 N+1 쿼리는 항목당 약 50ms를 추가한다"가 "느릴 수 있다"보다 낫다.
- **명백한 문제가 있는 접근에는 반대하라.** 아첨은 리뷰에서도 실패 모드다. 문제가 있으면 직접 말하고 대안을 제시한다.
- **override는 침착하게 받아들인다.** 작성자가 더 많은 맥락을 갖고 있고 동의하지 않는다면 그 판단을 존중한다. 사람을 비판하지 말고 코드에 대해 말하라.

## 의존성 절제

코드 리뷰에는 의존성 리뷰도 포함된다.

**새 의존성을 추가하기 전에**

1. 기존 스택으로 해결할 수 없는가? 대개는 된다.
2. 의존성의 크기는 어느 정도인가? 번들 영향까지 확인한다.
3. 적극적으로 유지보수되는가? 마지막 커밋과 열린 이슈를 본다.
4. 알려진 취약점이 있는가? `npm audit`로 확인한다.
5. 라이선스는 프로젝트와 호환되는가?

**규칙:** 표준 라이브러리와 기존 유틸리티를 새 의존성보다 우선한다. 모든 의존성은 부채다.

## 리뷰 체크리스트

```markdown
## Review: [PR/Change title]

### Context
- [ ] I understand what this change does and why

### Correctness
- [ ] Change matches spec/task requirements
- [ ] Edge cases handled
- [ ] Error paths handled
- [ ] Tests cover the change adequately

### Readability
- [ ] Names are clear and consistent
- [ ] Logic is straightforward
- [ ] No unnecessary complexity

### Architecture
- [ ] Follows existing patterns
- [ ] No unnecessary coupling or dependencies
- [ ] Appropriate abstraction level

### Security
- [ ] No secrets in code
- [ ] Input validated at boundaries
- [ ] No injection vulnerabilities
- [ ] Auth checks in place
- [ ] External data sources treated as untrusted

### Performance
- [ ] No N+1 patterns
- [ ] No unbounded operations
- [ ] Pagination on list endpoints

### Verification
- [ ] Tests pass
- [ ] Build succeeds
- [ ] Manual verification done (if applicable)

### Verdict
- [ ] **Approve** — Ready to merge
- [ ] **Request changes** — Issues must be addressed
```

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "동작하니까 충분하다" | 읽기 어렵거나, 불안전하거나, 설계가 잘못된 동작하는 코드는 시간이 갈수록 커지는 부채를 만든다. |
| "내가 짠 코드니까 맞는지 안다" | 작성자는 자기 가정에 눈이 멀기 쉽다. 모든 변경은 다른 시선을 거치는 편이 낫다. |
| "나중에 정리하겠다" | 나중은 오지 않는다. 리뷰가 품질 게이트다. 머지 후가 아니라 머지 전에 정리하게 하라. |
| "AI가 만든 코드니까 괜찮을 것이다" | AI 코드는 덜이 아니라 더 엄격하게 봐야 한다. 자신감 있고 그럴듯해 보여도 틀릴 수 있다. |
| "테스트가 통과하니 좋다" | 테스트는 필요조건이지 충분조건이 아니다. 아키텍처, 보안, 가독성 문제까지 잡아주지는 않는다. |

## Red Flags

- 어떤 리뷰도 없이 머지되는 PR
- 테스트 통과 여부만 보는 리뷰
- 실제 검토 흔적 없이 "LGTM"만 남기는 리뷰
- 보안 민감 변경인데 보안 관점 검토가 없는 경우
- "너무 커서 제대로 리뷰하기 어렵다"는 대형 PR
- 버그 수정 PR에 회귀 테스트가 없는 경우
- 심각도 라벨 없는 리뷰 코멘트. 무엇이 필수인지 불분명해진다
- "나중에 고칠게요"를 받아들이는 경우

## Verification

리뷰가 끝난 뒤에는 다음을 확인한다.

- [ ] 모든 Critical 이슈가 해결되었다.
- [ ] 모든 Important 이슈가 해결되었거나, 근거를 갖고 명시적으로 보류되었다.
- [ ] 테스트가 통과한다.
- [ ] 빌드가 성공한다.
- [ ] 검증 스토리가 기록되었다. 무엇이 바뀌었고 어떻게 확인했는지 남아 있다.

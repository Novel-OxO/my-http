# 명세 주도 개발

## Overview

코드를 쓰기 전에 구조화된 명세를 먼저 작성한다. 명세는 당신과 사람 엔지니어가 공유하는 기준 문서이며, 무엇을 왜 만드는지, 무엇이 완료 조건인지 정의한다. 명세 없이 코드를 쓰는 것은 추측에 기대는 일이다.

## When to Use

- 새 프로젝트나 기능을 시작할 때
- 요구사항이 모호하거나 불완전할 때
- 여러 파일이나 모듈에 걸쳐 변경이 발생할 때
- 아키텍처 결정을 내려야 할 때
- 구현에 30분 이상 걸릴 가능성이 있을 때

**When NOT to use:** 한 줄 수정, 오타 수정, 또는 요구사항이 자명하고 독립적인 변경에는 쓰지 않는다.

## 게이트형 워크플로

명세 주도 개발은 네 단계로 구성된다. 현재 단계가 검증되기 전에는 다음 단계로 넘어가지 않는다.

```
SPECIFY ──→ PLAN ──→ TASKS ──→ IMPLEMENT
   │          │        │          │
   ▼          ▼        ▼          ▼
 Human      Human    Human      Human
 reviews    reviews  reviews    reviews
```

### 1단계: Specify

높은 수준의 비전에서 시작한다. 요구사항이 구체화될 때까지 사람에게 확인 질문을 던진다.

**가정을 즉시 드러낸다.** 명세 내용을 쓰기 전에 무엇을 가정하고 있는지 먼저 적는다.

```
ASSUMPTIONS I'M MAKING:
1. 이건 네이티브 모바일이 아니라 웹 애플리케이션이다.
2. 인증은 JWT가 아니라 세션 쿠키를 사용한다.
3. 데이터베이스는 기존 Prisma 스키마를 기준으로 PostgreSQL이다.
4. 대상 브라우저는 최신 브라우저이며 IE11은 고려하지 않는다.
→ 틀렸다면 지금 바로 정정해 주세요. 아니면 이 가정을 기준으로 진행합니다.
```

모호한 요구사항을 조용히 채워 넣지 마라. 명세의 핵심 목적은 코드 작성 *이전* 에 오해를 드러내는 것이고, 가정은 가장 위험한 형태의 오해다.

**명세 문서는 아래 여섯 가지 핵심 영역을 포함해야 한다.**

1. **Objective**: 무엇을 왜 만드는가? 사용자는 누구인가? 성공은 어떤 상태인가?

2. **Commands**: 도구 이름만이 아니라 플래그까지 포함한 실제 실행 명령.
   ```
   Build: npm run build
   Test: npm test -- --coverage
   Lint: npm run lint --fix
   Dev: npm run dev
   ```

3. **Project Structure**: 소스 코드, 테스트, 문서가 어디에 위치하는가.
   ```
   src/           → 애플리케이션 소스 코드
   src/components → React 컴포넌트
   src/lib        → 공용 유틸리티
   tests/         → 단위/통합 테스트
   e2e/           → 종단간 테스트
   docs/          → 문서
   ```

4. **Code Style**: 문장 세 단락보다 실제 코드 한 조각이 더 낫다. 네이밍 규칙, 포맷팅 규칙, 좋은 출력 예시를 포함한다.

5. **Testing Strategy**: 어떤 프레임워크를 쓰는지, 테스트는 어디에 두는지, 커버리지 기대치와 어떤 문제를 어떤 수준의 테스트로 검증하는지 정의한다.

6. **Boundaries**: 세 단계로 나눈 경계 규칙.
   - **Always do:** 커밋 전 테스트 실행, 네이밍 규칙 준수, 입력 검증
   - **Ask first:** 데이터베이스 스키마 변경, 의존성 추가, CI 설정 변경
   - **Never do:** 비밀 정보 커밋, vendor 디렉터리 수정, 승인 없는 실패 테스트 삭제

**명세 템플릿**

```markdown
# Spec: [Project/Feature Name]

## Objective
[무엇을 왜 만드는지. 사용자 스토리나 승인 기준.]

## Tech Stack
[프레임워크, 언어, 주요 의존성과 버전]

## Commands
[build, test, lint, dev 전체 명령]

## Project Structure
[디렉터리 구조와 설명]

## Code Style
[예시 코드와 핵심 규칙]

## Testing Strategy
[프레임워크, 테스트 위치, 커버리지 요구사항, 테스트 수준]

## Boundaries
- Always: [...]
- Ask first: [...]
- Never: [...]

## Success Criteria
[완료 판단 기준. 구체적이고 테스트 가능해야 한다]

## Open Questions
[사람의 입력이 필요한 미해결 항목]
```

**지시사항을 성공 기준으로 다시 표현한다.** 요구가 모호하면, 측정 가능한 완료 조건으로 재구성한다.

```
REQUIREMENT: "대시보드를 더 빠르게 만들어라"

REFRAMED SUCCESS CRITERIA:
- 4G 환경에서 Dashboard LCP < 2.5s
- 초기 데이터 로드 < 500ms
- 로드 중 레이아웃 시프트 없음 (CLS < 0.1)
→ 이 목표들이 맞는지 확인해 주세요.
```

이렇게 해야 "빠르게"가 무엇인지 추측하지 않고, 명확한 목표를 향해 반복하고 수정할 수 있다.

### 2단계: Plan

검증된 명세를 바탕으로 기술 구현 계획을 작성한다.

1. 주요 구성요소와 그 의존 관계를 식별한다.
2. 구현 순서를 결정한다. 무엇을 먼저 만들어야 하는지 분명히 한다.
3. 리스크와 완화 전략을 적는다.
4. 병렬로 가능한 작업과 순차적으로 해야 하는 작업을 구분한다.
5. 단계 사이에 둘 검증 체크포인트를 정의한다.

계획은 사람이 읽고 "이 접근이 맞다" 또는 "이 부분을 바꿔라"라고 판단할 수 있을 정도로 검토 가능해야 한다.

### 3단계: Tasks

계획을 실제 구현 가능한 작은 작업으로 쪼갠다.

- 각 작업은 한 번의 집중 세션에서 끝낼 수 있어야 한다.
- 각 작업은 명시적인 승인 기준을 가져야 한다.
- 각 작업은 검증 방법을 포함해야 한다. 테스트, 빌드, 수동 확인 중 무엇인지 써야 한다.
- 작업 순서는 중요도보다 의존 관계를 기준으로 정한다.
- 한 작업이 대략 5개 이상의 파일을 동시에 건드리지 않도록 유지한다.

**작업 템플릿**

```markdown
- [ ] Task: [설명]
  - Acceptance: [완료되었을 때 반드시 참이어야 하는 조건]
  - Verify: [어떻게 확인할지 — 테스트 명령, 빌드, 수동 확인]
  - Files: [수정할 파일]
```

### 4단계: Implement

작업은 한 번에 하나씩 수행한다. 이때 `incremental-implementation`과 `test-principal` 스킬을 따른다. 또한 `context-engineering`을 사용해 각 단계에서 필요한 명세 조각과 소스 파일만 불러오고, 전체 명세를 한꺼번에 에이전트에게 밀어 넣지 않는다.

## 명세를 살아 있는 문서로 유지하기

명세는 일회성 산출물이 아니라 계속 관리하는 문서다.

- **결정이 바뀌면 갱신한다.** 데이터 모델을 바꿔야 한다면, 구현 전에 명세를 먼저 수정한다.
- **범위가 바뀌면 갱신한다.** 추가되거나 제외된 기능을 명세에 반영한다.
- **명세도 버전 관리에 넣는다.** 코드와 같이 저장소에 커밋한다.
- **PR에서 명세를 참조한다.** 각 PR이 명세의 어느 부분을 구현하는지 링크한다.

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "이건 단순해서 명세가 필요 없다" | 단순한 작업은 긴 명세가 필요 없을 뿐, 승인 기준은 여전히 필요하다. 두 줄짜리 명세도 괜찮다. |
| "코드부터 쓰고 나중에 명세를 적겠다" | 그건 사후 문서화지 명세가 아니다. 명세의 가치는 코드 작성 전에 사고를 정리하는 데 있다. |
| "명세를 쓰면 속도가 느려진다" | 15분 명세는 몇 시간의 재작업을 막는다. 15분의 워터폴이 15시간 디버깅보다 낫다. |
| "어차피 요구사항은 바뀐다" | 그래서 명세를 살아 있는 문서로 유지하는 것이다. 오래된 명세도 없는 것보다는 낫다. |
| "사용자는 자기가 원하는 걸 안다" | 명확한 요청에도 암묵적 가정은 있다. 명세는 그 가정을 밖으로 끌어낸다. |

## Red Flags

- 어떤 요구사항도 문서화하지 않은 채 바로 코드부터 쓰는 경우
- "그냥 만들기 시작할까요?"라고 묻지만 완료 조건은 정의하지 않은 경우
- 명세나 작업 목록에 없는 기능을 구현하는 경우
- 아키텍처 결정을 기록 없이 진행하는 경우
- "뭘 만들지 너무 뻔하다"는 이유로 명세를 건너뛰는 경우

## Verification

구현 단계로 넘어가기 전에 다음을 확인한다.

- [ ] 명세가 여섯 가지 핵심 영역을 모두 다룬다.
- [ ] 사람이 명세를 검토하고 승인했다.
- [ ] 성공 기준이 구체적이고 테스트 가능하다.
- [ ] 경계 규칙(Always/Ask First/Never)이 정의되어 있다.
- [ ] 명세가 저장소 내 파일로 저장되어 있다.

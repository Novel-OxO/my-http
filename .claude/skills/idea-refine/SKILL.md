# 아이디어 정제

## Overview

막연한 아이디어를 바로 구현 계획으로 밀어 넣지 않고, 발산과 수렴을 거쳐 실제로 만들 가치가 있는 방향으로 다듬는다. 좋은 아이디어 정제는 "생각을 많이 하는 것"이 아니라, 누구의 어떤 문제를 어떤 범위로 풀지 명확하게 만드는 일이다.

## When to Use

- 대략적인 컨셉은 있는데 무엇을 만들지 아직 흐릴 때
- 기능 제안이나 제품 아이디어를 구체적인 방향으로 좁혀야 할 때
- 명세 작성 전에 문제 정의와 MVP 범위를 먼저 다듬어야 할 때
- 사용자 가치, 제약, 차별점이 아직 불분명할 때
- 여러 방향이 가능해서 무엇을 버리고 무엇을 남길지 정해야 할 때

**When NOT to use:** 이미 승인된 명세와 구현 작업 목록이 있는 상태라면 `spec-driven-development` 또는 `planning-and-task-breakdown`으로 진행한다. 단순한 문구 수정이나 범위가 자명한 작업에는 쓰지 않는다.

## 아이디어 정제 흐름

아이디어 정제는 세 단계로 진행한다.

```text
RAW IDEA
   │
   ├── Phase 1: Understand & Expand
   │        문제를 다시 정의하고, 질문하고, 변형을 만든다
   │
   ├── Phase 2: Evaluate & Converge
   │        방향을 묶고, 압박 테스트하고, 가정을 드러낸다
   │
   └── Phase 3: Sharpen & Ship
            한 장짜리 문서로 정리해 다음 작업으로 넘긴다
```

### Phase 1: Understand & Expand

**Goal:** 아이디어를 넓게 열어 보고, 실제로 풀 문제를 선명하게 만든다.

1. 아이디어를 먼저 다시 서술한다.
   단순 재진술이 아니라, "우리는 무엇을 바꾸려는가?"가 드러나야 한다.

2. 아이디어를 짧은 "How Might We" 문제 정의로 바꾼다.

```text
RAW: "한국어 스킬 저장소를 만들고 싶다"

HMW: "How might we make upstream agent skills immediately usable for a Korean-speaking Codex workflow without breaking skill discovery?"
```

3. 사용자에게 3~5개의 선명화 질문을 한다. 그 이상은 대개 과하다.
   질문은 아래 축에 집중한다.

- 이건 정확히 누구를 위한 것인가?
- 성공은 어떤 상태인가?
- 시간, 기술, 리소스 제약은 무엇인가?
- 이미 시도한 방식이 있는가?
- 왜 지금 이 문제를 푸는가?

4. 첫 답을 그대로 믿지 말고, 5~8개의 변형 방향을 만든다.
   아래 렌즈를 상황에 맞게 선택적으로 쓴다.

- 반전: 정반대로 하면 어떻게 되는가?
- 제약 제거: 시간, 예산, 기술 제약이 없다면?
- 사용자 전환: 다른 사용자라면 무엇이 달라지는가?
- 결합: 인접 아이디어와 합치면?
- 단순화: 10배 단순한 버전은?
- 확장: 대규모로 가정하면?
- 전문가 렌즈: 도메인 전문가가 당연하다고 여길 것은?

5. 아이디어는 목록으로만 나열하지 않는다.
   각 변형 방향마다 "왜 이 방향이 존재하는가"를 설명한다.

### Phase 2: Evaluate & Converge

**Goal:** 넓힌 아이디어 중 실제로 검토할 가치가 있는 2~3개 방향으로 수렴한다.

1. 사용자가 반응한 변형 방향을 묶어서 2~3개의 distinct direction으로 정리한다.
   서로 이름만 다른 유사안이면 안 된다.

2. 각 방향을 아래 세 기준으로 압박 테스트한다.

- 사용자 가치: 누가 얼마나 강하게 이득을 보는가? painkiller인가 vitamin인가?
- 실행 가능성: 기술 비용, 리소스 비용, 가장 어려운 부분은 무엇인가?
- 차별성: 왜 이 방향을 굳이 선택해야 하는가? 기존 대안에서 갈아탈 이유가 있는가?

3. 숨은 가정을 명시적으로 적는다.

- 무엇이 사실이라고 베팅하고 있는가?
- 무엇이 이 아이디어를 망칠 수 있는가?
- 지금은 일부러 무시하는 것은 무엇이며, 왜 지금은 무시해도 되는가?

4. 약한 아이디어는 약하다고 말한다.
   좋은 아이디어 파트너는 무조건 지지하지 않는다. 복잡하고 가치가 약한 방향이라면, 왜 약한지 구체적으로 설명한다.

### Phase 3: Sharpen & Ship

**Goal:** 다음 단계로 넘길 수 있는 짧고 강한 산출물을 만든다.

최종 산출물은 한 장짜리 Markdown 문서다. 구현을 시작하는 문서가 아니라, 명세나 계획으로 이어질 수 있는 정제된 방향 문서다.

```markdown
# [Idea Name]

## Problem Statement
[한 문장짜리 How Might We 문제 정의]

## Recommended Direction
[선택한 방향과 이유. 2~3문단 이내]

## Key Assumptions To Validate
- [ ] [가정 1 — 어떻게 검증할지]
- [ ] [가정 2 — 어떻게 검증할지]
- [ ] [가정 3 — 어떻게 검증할지]

## MVP Scope
[핵심 가정을 검증하는 최소 범위. 무엇이 들어가고 무엇이 빠지는지]

## Not Doing
- [항목 1] — [이번에는 하지 않는 이유]
- [항목 2] — [이번에는 하지 않는 이유]
- [항목 3] — [이번에는 하지 않는 이유]

## Open Questions
- [명세 작성 전에 풀어야 할 질문]
```

**`Not Doing` 목록은 필수다.** 집중은 좋은 아이디어를 더하는 것보다, 지금 하지 않을 것을 분명히 하는 데서 생긴다.

문서를 저장할 때는 사용자에게 먼저 묻는다. 기본 경로는 `docs/ideas/[idea-name].md`로 제안하되, 확인 없이 저장하지 않는다.

## 아이디어 렌즈 선택법

모든 렌즈를 기계적으로 다 돌리지 말고, 현재 아이디어에 맞는 것만 고른다.

| Lens | Ask This When | Useful Prompt |
|---|---|---|
| Inversion | 지금 방향이 너무 당연하게 느껴질 때 | "정반대로 하면 무엇이 드러나나?" |
| Constraint Removal | 제약 때문에 사고가 좁아졌을 때 | "제약이 없다면 가장 자연스러운 해결은?" |
| Audience Shift | 사용자 정의가 흐릴 때 | "다른 사용자라면 가장 중요한 가치가 무엇으로 바뀌나?" |
| Simplification | 너무 많은 기능이 붙기 시작할 때 | "핵심 가정 하나만 검증하려면 무엇만 남기나?" |
| 10x Scale | 구조적 한계를 보고 싶을 때 | "이게 100배 커지면 어디가 먼저 무너지나?" |
| Expert Lens | 도메인 이해가 얕을 때 | "도메인 전문가가 보기엔 무엇이 너무 순진한가?" |

## 코드베이스 안에서 아이디어 정제할 때

프로젝트 안에서 아이디어를 다듬고 있다면, 공중에 뜬 제안을 만들지 말고 현재 구조를 제약으로 받아들인다.

- 기존 아키텍처와 패턴을 먼저 읽는다.
- 이미 있는 모듈, naming, 접근 방식과 충돌하는지 본다.
- "새로 만드는 게 더 멋져 보인다"는 이유로 현재 코드베이스를 무시하지 않는다.
- 기존 구조를 깨야 한다면 그 이유를 아이디어 단계에서 드러낸다.

즉, 아이디어 정제는 자유로운 브레인스토밍이지만, 프로젝트 안에서는 현실을 모른 척하는 연습이 아니다.

## 다음 단계로 넘기는 기준

아이디어 정제의 목적은 구현이 아니라 다음 의사결정을 쉽게 만드는 것이다.

- 문제와 사용자가 선명해졌다면 `spec-driven-development`로 넘긴다.
- 이미 방향은 정해졌고 작업 분해가 필요하다면 `planning-and-task-breakdown`으로 넘긴다.
- 핵심 가정을 검증하는 실험이 먼저라면, 그 실험 자체를 작은 spec으로 정의한다.

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "일단 만들면서 생각해 보자" | 그건 아이디어 정제가 아니라 구현으로 문제 정의를 대신하는 것이다. 대개 재작업으로 돌아온다. |
| "이건 뻔한 아이디어라 질문이 필요 없다" | 누가 왜 쓰는지 흐리면, 뻔한 아이디어일수록 쉽게 잘못 만든다. |
| "변형 방향을 많이 내면 더 창의적이다" | 20개의 얕은 방향보다 5~8개의 잘 생각한 방향이 낫다. |
| "사용자가 원하니까 그대로 가면 된다" | 좋은 파트너는 주문을 받아 적는 사람이 아니라, 약한 가정과 복잡도를 드러내는 사람이다. |
| "가정은 나중에 검증하면 된다" | 검증되지 않은 가정을 숨긴 채 방향을 고르면, 나중에 전체 계획이 흔들린다. |

## Red Flags

- "누구를 위한 것인가?"가 끝까지 모호한 상태
- 첫 아이디어를 거의 수정하지 않고 바로 채택하는 상태
- 장점만 있고 trade-off가 없는 제안
- 가정, 리스크, `Not Doing` 목록이 없는 산출물
- 복잡한 안을 더 세련돼 보인다는 이유로 선호하는 태도
- 코드베이스 안의 제약을 무시하고 새 구조만 상상하는 상태

## Verification

아이디어 정제를 마친 뒤에는 다음을 확인한다.

- [ ] 한 문장의 "How Might We" 문제 정의가 있다.
- [ ] 대상 사용자와 성공 기준이 드러나 있다.
- [ ] 첫 아이디어만 본 것이 아니라 여러 방향을 탐색했다.
- [ ] 숨은 가정이 명시되어 있고, 어떻게 검증할지 적혀 있다.
- [ ] `Not Doing` 목록이 있어 범위 밖 항목이 분명하다.
- [ ] 결과물이 다음 단계로 넘길 수 있는 Markdown 산출물 형태다.
- [ ] 구현이나 저장은 사용자 확인 이후에만 진행한다.

# 스킬 해부도 (Skill Anatomy)

이 문서는 agent-skills 스킬 파일의 구조와 형식을 설명합니다. 새 스킬을 기여하거나 기존 스킬을 이해할 때 가이드로 사용하세요.

## 파일 위치

모든 스킬은 `skills/` 아래 자체 디렉터리에 존재합니다:

```
skills/
  skill-name/
    SKILL.md           # 필수: 스킬 정의
    supporting-file.md # 선택: 필요 시 로드되는 참조 자료
```

## SKILL.md 형식

### 프론트매터 (필수)

```yaml
---
name: skill-name-with-hyphens
description: 에이전트를 [작업/워크플로] 과정에 안내합니다. [특정 트리거 조건]에서 사용합니다.
---
```

**규칙:**
- `name`: 소문자, 하이픈 구분. 디렉터리 이름과 일치해야 함.
- `description`: 스킬이 무엇을 하는지 (3인칭)로 시작하고, 하나 이상의 명확한 "사용 시점" 트리거 조건을 포함합니다. *무엇*과 *언제*를 모두 담습니다. 최대 1024자.

**왜 중요한가:** 에이전트는 description을 읽어 스킬을 발견합니다. description은 시스템 프롬프트에 주입되므로, 스킬이 무엇을 제공하는지와 언제 활성화할지 모두 말해야 합니다. 워크플로를 요약하지 마세요 — description에 프로세스 단계가 들어가면 에이전트가 전체 스킬을 읽지 않고 요약만 따를 수 있습니다.

### 표준 섹션 (권장 패턴)

```markdown
# 스킬 제목

## Overview
이 스킬이 무엇을 하며 왜 중요한지 1-2문장으로 설명.

## When to Use
- 트리거 조건 불릿 목록 (증상, 작업 유형)
- 사용하지 않아야 할 때 (제외 사항)

## [핵심 프로세스 / 워크플로 / 단계]
번호 매겨진 단계 또는 단계로 나눈 주요 워크플로.
도움이 되는 곳에 코드 예시 포함.
결정 지점이 있는 곳에 (ASCII) 플로우차트 사용.

## [특정 기법 / 패턴]
특정 시나리오를 위한 상세 지침.
코드 예시, 템플릿, 구성.

## Common Rationalizations
| 합리화 | 실제 |
|---|---|
| 에이전트가 단계 스킵에 쓰는 변명 | 그 변명이 왜 틀렸는지 |

## Red Flags
- 스킬이 위반되고 있음을 나타내는 행동 패턴
- 리뷰 중 주시할 것들

## Verification
스킬 프로세스 완료 후 확인:
- [ ] 종료 기준 체크리스트
- [ ] 증거 요구 사항
```

## 섹션의 목적

### Overview
스킬의 "엘리베이터 피치". 답해야 할 질문: 이 스킬은 무엇을 하며, 에이전트가 왜 따라야 하는가?

### When to Use
에이전트와 사람이 이 스킬이 현재 작업에 적용되는지 판단하도록 돕습니다. 긍정 트리거 ("X일 때 사용")와 부정 제외 ("Y에는 사용 금지") 모두 포함.

### Core Process
스킬의 심장. 에이전트가 따르는 단계별 워크플로입니다. 모호한 조언이 아닌 구체적이고 실행 가능해야 합니다.

**좋음:** "`npm test`를 실행하고 모든 테스트가 통과하는지 확인"
**나쁨:** "테스트가 잘 되는지 확인"

### Common Rationalizations
잘 만들어진 스킬의 가장 특징적인 부분. 에이전트가 중요한 단계를 스킵하려고 쓰는 변명과 그에 대한 반박입니다. 에이전트가 프로세스를 피해가려 합리화하는 것을 막습니다.

에이전트가 "테스트는 나중에 추가할게요" 또는 "간단하니 스펙 스킵해도 돼요"라고 말했던 모든 순간을 떠올리고 — 사실에 기반한 반론과 함께 여기에 적으세요.

### Red Flags
스킬이 위반되고 있음을 보여주는 관찰 가능한 신호. 코드 리뷰와 자기 모니터링에 유용합니다.

### Verification
종료 기준. 에이전트가 스킬 프로세스 완료를 확인하는 체크리스트. 모든 체크박스는 증거(테스트 출력, 빌드 결과, 스크린샷 등)로 검증 가능해야 합니다.

## 보조 파일

보조 파일은 다음 경우에만 생성:
- 참조 자료가 100줄 초과 (메인 SKILL.md를 집중시킴)
- 코드 도구나 스크립트가 필요
- 체크리스트가 별도 파일로 분리할 만큼 김

50줄 미만이면 패턴과 원칙은 인라인으로 유지하세요.

## 작성 원칙

1. **지식보다 프로세스.** 스킬은 워크플로이지 참조 문서가 아닙니다. 사실이 아닌 단계.
2. **일반보다 구체.** "`npm test` 실행"이 "테스트 확인"을 이깁니다.
3. **가정보다 증거.** 모든 검증 체크박스는 증명이 필요합니다.
4. **합리화 방지.** 스킵할 만한 모든 단계는 합리화 테이블에 반론이 있어야 합니다.
5. **점진적 노출.** 메인 SKILL.md가 진입점. 보조 파일은 필요할 때만 로드.
6. **토큰 의식.** 모든 섹션은 포함 이유를 정당화해야 합니다. 제거해도 에이전트 행동이 바뀌지 않으면 제거하세요.

## 네이밍 컨벤션

- 스킬 디렉터리: `lowercase-hyphen-separated`
- 스킬 파일: `SKILL.md` (항상 대문자)
- 보조 파일: `lowercase-hyphen-separated.md`
- 참조: 스킬 디렉터리 내부가 아닌 프로젝트 루트의 `references/`에 저장

## 크로스 스킬 참조

다른 스킬은 이름으로 참조:

```markdown
테스트 작성은 `test-principal` 스킬을 따릅니다.
빌드가 깨지면 `debugging-and-error-recovery` 스킬을 사용합니다.
```

스킬 간 내용을 복제하지 말고 — 대신 참조하고 링크하세요.
